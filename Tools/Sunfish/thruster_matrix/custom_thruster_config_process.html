Custom ArduSub Thruster Configuration Process

Prepared 2026-07-12. Example vehicle: Zoda. Source artifacts: Tools/Sunfish/thruster_matrix/zoda.json, Tools/Sunfish/thruster_matrix/thruster_matrix.py, libraries/AP_Motors/AP_Motors6DOF.h, and libraries/AP_Motors/AP_Motors6DOF.cpp.

This document explains the path from a physical thruster layout to a working ArduPilot 6DOF motor setup. It is meant for the next engineer who needs to create a custom thruster configuration, generate the mixer factors, add the frame to ArduPilot, and bench-test MOTx_DIRECTION so the vehicle drives the way the controller expects.

Goal Convert measured thruster geometry into ArduPilot mixer factors.
Key output A block of add_motor_raw_6dof(...) calls in AP_Motors6DOF.cpp.
Final validation Bench-test every motor direction, then test each vehicle axis.

Why This Process Exists

ArduPilot does not know where custom vehicle thrusters are mounted. It only knows the factors we give it. If those factors do not match the physical vehicle, a command like "move forward" or "pitch up" can produce unwanted yaw, roll, or reverse thrust. For an underwater vehicle this quickly becomes hard to diagnose because the controller, motor direction parameters, thruster handedness, and wiring can all look like possible causes.

The process below separates the problem into two layers. First, generate a geometry-based thruster allocation matrix. Second, use bench tests to make sure each physical thruster's output sign matches the matrix by setting MOTx_DIRECTION correctly.

Coordinate And Sign Convention

Use the vehicle body frame for all measurements and orientations:

  • F / +X: forward
  • R / +Y: right
  • D / +Z: down

The orientation field in the JSON describes the force on the vehicle, not the water flow. A vertical thruster that pushes water down applies upward force to the vehicle, so it should use "pitch": -90.0 and will normally produce a negative D factor.

The roll, pitch, and yaw columns generated for add_motor_raw_6dof() follow ArduPilot's mixer convention. For example, a front vertical thruster that lifts the bow creates a nose-up physical moment, but its ArduPilot pitch factor is negative. This matches the existing ArduSub frame tables and keeps the controller command sign consistent.

The moment calculation uses the chosen origin. Ideally this is the centre of gravity. If the centre of gravity is not known yet, use a clearly documented provisional origin and update the matrix once the real centre of gravity is measured.

Step 3: Add A Custom Frame In ArduPilot

Add a frame enum in libraries/AP_Motors/AP_Motors6DOF.h. For a dedicated Zoda frame, prefer a named enum such as SUB_FRAME_ZODA_6DOF rather than overloading SUB_FRAME_CUSTOM. This makes the frame selectable and reviewable without hiding the vehicle identity. 

typedef enum {
    SUB_FRAME_BLUEROV1,
    SUB_FRAME_VECTORED,
    SUB_FRAME_VECTORED_6DOF,
    SUB_FRAME_VECTORED_6DOF_90DEG,
    SUB_FRAME_SIMPLEROV_3,
    SUB_FRAME_SIMPLEROV_4,
    SUB_FRAME_SIMPLEROV_5,
    SUB_FRAME_ZODA_6DOF,
    SUB_FRAME_CUSTOM
} sub_frame_t;

Then add a matching case in libraries/AP_Motors/AP_Motors6DOF.cpp and paste the generated matrix there: 

case SUB_FRAME_ZODA_6DOF:
    _frame_class_string = "ZODA_6DOF";
    //                 Motor #          Roll    Pitch      Yaw       D       F       R  Test

    add_motor_raw_6dof(AP_MOTORS_MOT_4,        0,   0.129f,   0.962f,        0,   1.000f,        0, 4); // Forward thruster at rear left
    add_motor_raw_6dof(AP_MOTORS_MOT_5,   1.000f,  -1.000f,        0,  -1.000f,        0,        0, 5); // Front-right vertical
    add_motor_raw_6dof(AP_MOTORS_MOT_6,  -1.000f,  -1.000f,        0,  -1.000f,        0,        0, 6); // Front-left vertical
    add_motor_raw_6dof(AP_MOTORS_MOT_7,   1.000f,   0.604f,        0,  -1.000f,        0,        0, 7); // Rear-right vertical

Step 4: Understand What The Matrix Does Not Prove

The matrix says how ArduPilot should allocate vehicle-level commands to thrusters. It does not prove that the real installed motors spin in the expected direction. Wiring, ESC setup, prop installation, and MOTx_DIRECTION can still invert an individual thruster.

Treat the matrix as the intended allocation and MOTx_DIRECTION as the per-motor sign correction needed to make the physical vehicle match that allocation.

Step 5: Bench-Test MOTx_DIRECTION

Test motor direction before any in-water stability testing. The goal is to confirm the force on the vehicle, not just the prop spin direction.

  1. Secure the vehicle so a short motor pulse cannot move it unexpectedly.
  2. Use a low output motor test to pulse one motor at a time.
  3. Observe the force direction on the vehicle or the water flow direction if testing in water.
  4. Compare that force to the intended positive thrust direction in the JSON.
  5. If the force is opposite, flip that motor's MOTx_DIRECTION.
  6. Repeat for all eight motors.
Do not use MOTx_DIRECTION to hide a wrong geometry matrix. Use it only to correct an individual installed thruster whose physical output sign is reversed.

Vertical motors 5-8When commanded for upward force, each pushes water down and lifts its corner.

Yaw commandHorizontal thrusters oppose in a way that rotates the vehicle without large net translation.
F/R/D commandsThrusters combine to produce mostly forward, right, or down/up vehicle motion.

Step 6: Get To A Stable Vehicle

Once individual MOTx_DIRECTION values are correct, test whole-axis commands at low gain and low thrust. The first goal is not perfect control. The first goal is that every axis moves in the expected direction and does not strongly excite the wrong axis.

  1. Confirm neutral output is stable and no thruster creeps.
  2. Command small D, F, and R translations and verify direction.
  3. Command small roll, pitch, and yaw corrections and verify sign.
  4. If an entire axis is reversed, revisit the matrix/sign convention before tuning gains.
  5. If one motor fights the others, revisit that motor's MOTx_DIRECTION.
  6. Only start controller tuning after direction and allocation are correct.

What This Supports And What It Does Not

This process supports a repeatable custom thruster configuration workflow. It makes the mixer traceable back to geometry and gives the team a clear bench procedure for direction validation. It does not replace in-water tuning, and it does not prove the centre of gravity is correct if that origin was only estimated.

If the centre of gravity changes because batteries, payload, buoyancy, or ballast change, update the thruster positions relative to the new centre of gravity and regenerate the matrix.
